# Основная и тестовая версии

## Правило работы

| Версия | Ветка GitHub | Приложение Amvera | Данные |
|---|---|---|---|
| Основная (PROD) | `main` | Существующая игра | Существующий диск и результаты студентов |
| Тестовая (DEV) | `dev` | Новое отдельное приложение | Новый отдельный диск и тестовые результаты |

Новые изменения сначала делаются в `dev`. Основная версия обновляется только
после проверки и отдельного переноса изменений в `main`. Само создание ветки
не создаёт приложение в Amvera. В рамках подготовки ветка `main` не меняется.

## Создать тестовый сайт в Amvera

1. Существующее приложение игры оставить подключённым к `main`. Не менять его
   переменные, домен, диск или данные ради тестовой версии.
2. Создать **новое приложение**, например `radiotech-game-dev`, с отдельным
   тарифом. Оно оплачивается отдельно по условиям Amvera; стоимость проверить
   перед созданием. Не увеличивать число реплик существующей игры.
3. Подключить тот же репозиторий `nohopeandlove/chrt_game`, но выбрать ветку **`dev`**.
4. Выбрать Docker / Dockerfile: `Dockerfile`, `containerPort: 3000`,
   `persistenceMount: /data`. Это `/data` нового приложения с новым постоянным
   диском, а не диск существующей основной игры. Одна реплика.
5. Добавить переменные этапа **«Запуск»**:

   | Название | Значение |
   |---|---|
   | `APP_ENV` | `dev` |
   | `NODE_ENV` | `production` |
   | `HOST` | `0.0.0.0` |
   | `PORT` | `3000` |
   | `COOKIE_SECURE` | `true` |
   | `DATA_DIR` | `/data` |

   Дополнительно для первого входа преподавателя — секретный `TEACHER_SETUP_CODE`:
   новый случайный код из 32 латинских букв и цифр. Не копировать секреты основной
   игры. После настройки удалить переменную. Инструкция: [HOSTING.md](HOSTING.md).
6. Подключить новый бесплатный HTTPS-домен Amvera. Не привязывать к тестовому
   приложению действующий домен основной игры. Использовать отдельный адрес,
   а не путь `/dev` внутри основного сайта.
7. Дождаться запуска. Проверить `/api/environment`: должен быть ответ
   `{"environment":"dev"}`. Игра и кабинет должны показывать «Тестовая версия (DEV)».
8. На новом адресе `/teacher/` создать отдельную тестовую учётную запись. Не
   переносить туда настоящие результаты студентов; использовать вымышленные данные.

В основном приложении после будущего выпуска этой конфигурации можно указать
`APP_ENV=prod`; это также значение по умолчанию. `NODE_ENV=production` нужно
оставить в обоих развернутых приложениях: оно определяет режим Node.js, а не
принадлежность данных к основной или тестовой версии.

## Что разделено

- У приложений разные адреса, браузерные сохранения, постоянные диски, SQLite-базы,
  пароли преподавателя и сессии. Имя cookie DEV отличается даже при локальной
  проверке на одном хосте.
- Синхронизация отправляет результаты на текущий адрес игры; адрес основной базы
  не прописывается в тестовой версии.
- Каталог данных помечается средой. При попытке открыть диск другой среды сервер
  откажется запускаться до открытия базы. DEV также не откроет старую базу без
  отметки среды: для него нужен новый пустой диск. Не удалять отметку ради обхода
  ошибки; указать правильный отдельный диск.
- Метка среды — дополнительная проверка, а не замена отдельного хостинга и диска.

## Как добавлять изменения и выпускать их

1. В GitHub переключиться с `main` на **`dev`** до редактирования файла. Например,
   публичный текст тестовой версии — `docs/ABOUT.md` в ветке `dev`.
2. Сохранить изменения в `dev`. Amvera тестового приложения должна быть подключена
   к этой ветке и обновлять только тестовую версию.
3. Пройти изменённые задания на тестовом адресе; проверить кабинет, сохранение,
   телефон и нужные варианты ответов.
4. После успешной проверки создать Pull Request **из `dev` в `main`** в GitHub.
   Проверки GitHub Actions должны пройти. Выпуск подтверждается отдельно;
   автоматического слияния в `main` нет.
5. После слияния Amvera основной игры пересобирает новую версию из `main`.
   Переносятся код и контент, **не тестовая база или результаты**. Основной
   постоянный диск сохраняется.
6. После выпуска обновить `dev` из `main`, если ветки разошлись. Если кто-то
   отредактировал `main` напрямую, сначала перенести эти изменения в `dev`,
   чтобы не потерять их при следующем выпуске.

Включите в настройках GitHub защиту `main`: требование Pull Request и успешных
проверок перед слиянием. Файл workflow добавлен в проект, но сам по себе не
включает защиту ветки; настройка защиты в GitHub пока не выполнена.

Перед существенным выпуском сделать резервную копию основной базы средствами
Amvera. Откат кода — отдельное обновление `main` проверенной версией. Если выпуск
в будущем меняет формат базы, одного отката кода может быть недостаточно: нужна
проверенная процедура миграции и восстановления. Разделение сред не является
гарантией отсутствия ошибок после выпуска.

## Локальная проверка без риска для основной базы

```sh
docker compose -f compose.dev.yaml up --build -d
```

Тестовая игра: http://localhost:8081 . Отдельный Compose-проект `chrt-game-dev`
и отдельный том `dev-data`; обычный compose.yaml основной игры не используется.
Чтобы получить код тестового преподавателя:

```sh
docker compose -f compose.dev.yaml exec game node server/manage.mjs setup-code
```

Без Docker: `APP_ENV=dev npm start` на Linux или `$env:APP_ENV="dev"; npm start`
в PowerShell; папка по умолчанию `data-dev/`. Для одновременного запуска с основной
версией назначить отдельный `PORT` и адрес API dev-сервера самостоятельно.

Проверки: `npm run check`, `npm run build`, `node tools/server-smoke.mjs`,
`node tools/environments-smoke.mjs`. Проверка метки и её отображения на телефоне:
`tools/environment-browser-smoke.mjs` с внешним Playwright. При push в `dev`
и Pull Request в `main` запускаются проверки GitHub Actions; они не публикуют
приложение и не обращаются к рабочей базе.
